fix(store): close the two remaining ways values could be erased

A five-pass review of the value-preservation guarantees, each pass hunting a
different loss vector. Two real holes found, both now closed.

HOLE 1 - the quarantine could itself silently fail.
The unreadable-value quarantine swallowed every error, so if the copy could not
be written (storage full, private mode) the app still returned null, rehydrated
onto defaults, and overwrote the unreadable value on the next tick: the exact
destruction the quarantine exists to prevent. quarantine() now reports whether
it preserved anything, and a failure raises dataPreservationFailed, which is
surfaced with its own message rather than a reassuring "we saved a copy".

HOLE 2 - the web app never asked the browser to keep the data.
localStorage is evictable. Browsers may and do clear it for sites they judge
low priority, under disk pressure, or after long absence, and the app never
asked otherwise. For a product whose entire promise is that prayer history is
never lost, that is an unacceptable dependency on luck. The app now calls
navigator.storage.persist() at startup and records the answer, warning the user
in Settings if it was refused. (The Android build writes to app-private storage,
which the OS does not evict, so this is a web-only hole - confirmed by the
existing merged-manifest audit.)

Verified clean on the other passes, rather than assumed:
- no clear/reset/wipe path exists anywhere in src (the only .clear() is an audio
  buffer)
- setProfile merges a patch, and setPrayerTotals/setSpiritTotals already
  max-merge, so neither can zero data
- Android persists synchronously with no debounce, so a hard process kill
  cannot lose a write
- prayerDayStats[day][prayerId] is a plain number, so the two-level max-merge in
  neverLoseData is correct for it

Plus an explicit test for the case that was only reasoned about: a lossy schema
upgrade (a future migrate() that drops fields) rehydrates emptied counters into
memory, and the write guard folds them against what is on disk, so a Play update
cannot erase history. 59 assertions now.
